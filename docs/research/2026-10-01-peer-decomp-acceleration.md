# What is accelerating peer decompilations?

Research date: 2026-10-01 (UTC snapshots). Scope: matching decompilation practices that could improve [DW4's verified GameCube recovery](../../AGENTS.md), not a claim that a dashboard percentage measures engineering effort.

## Method and measurement limits

I screened 24 recently updated projects from the [decomp.dev project index](https://decomp.dev/projects), emphasizing GameCube/Wii projects with PowerPC and Metrowerks/CodeWarrior workflows. For each candidate I read its version-specific [history JSON](https://decomp.dev/PrimeDecomp/prime/GM8E01_00.json?mode=history), comparing the **first recorded snapshot on or after September 1** with a fixed latest snapshot on September 30 or October 1. The table uses exact `matched_code` and `complete_code` byte counts, not rounded percentages, fuzzy scores, function counts, or aggregate percentages across game versions. The observation intervals differ where reports were not uploaded on September 1; this is a screened comparison, not a site-wide ranking or a rate normalized by contributor-hours. Repository commits, source, documentation, and CI are the evidence for *how* progress occurred. A report can move after source is merely linked, a library is added, the denominator changes, or reporting rules change; those cases are called out below.

The point estimates are snapshots, not proof of identical review standards. For example, [Persona 4's history](https://decomp.dev/Raikaru/Persona4-Decompilation/SLUS_217.82.json?mode=history) shows +2,141,784 linked bytes on one September 25 report and −2,532,776 on a later one when the project [changed the rule to count only ASM-free C files as fully linked](https://github.com/Raikaru/Persona4-Decompilation/commit/f490439f). Its net linked delta cannot be compared naively with the GameCube figures. [FFCC's report](https://decomp.dev/zcanann/FFCC-Decomp/GCCP01.json?mode=history) expands its code denominator by 166,352 B while adding GBA components in [a staging merge](https://github.com/zcanann/FFCC-Decomp/commit/7787c209); that merge credits a Claude co-author, which establishes participation but does not isolate AI-caused matching gains. Fresh forks with only a few days of history, such as [the BFBB AI fork](https://decomp.dev/zcanann/bfbb/GQPE78.json?mode=history), were not treated as month-long velocity observations.

## The current agentic burst

The short-lived campaigns deserve separate treatment because they answer a different question: how are repositories converting abundant compute and parallel agents into verified bytes? Their rates are not month-long trends, but the workflows are directly observable.

These campaigns share an architecture rather than a magic matching algorithm:

1. A coordinator owns integration, target assignment and whole-build truth.
2. Workers own disjoint TUs or domain buckets and compile privately.
3. The hot loop emits compact, machine-readable mismatch evidence in seconds.
4. Repeated compiler behavior is written into a playbook instead of rediscovered.
5. Shared declarations, donor maps/DWARF, other versions and existing nonmatching source create many parallel-ready targets.
6. Exact object/data checks and the retail executable checksum remain the publication boundary.

## Mechanisms supported by first-party evidence

1. **Prior source and symbol knowledge reduce discovery time.** Prime can cross-check a [demo linker map](https://github.com/PrimeDecomp/prime/blob/main/docs/map.md), shared Ghidra definitions and a nearly complete nonmatching reference; the map even lists TU references and candidate inlines, though its early-demo provenance limits retail claims. Wind Waker has [prerelease debug maps and a guide to their inline limits](https://github.com/zeldaret/tww/blob/main/docs/decompiling.md#inline-functions-and-how-to-read-the-debug-maps). Strikers Charged records exactly where predecessor source shapes or names helped, while [requiring R4QE01 evidence for changed fields and behavior](https://github.com/yannicksuter/mscharged-decomp/blob/main/docs/PROVENANCE.md). These inputs can make a large verified patch inexpensive relative to reverse engineering from a stripped retail binary alone.
2. **Shared declarations and coherent TUs multiply matches.** Prime's [animation/container patch](https://github.com/PrimeDecomp/prime/commit/a2c201d5) changes shared headers and symbols as well as implementation, while Echoes' [SDK batch](https://github.com/PrimeDecomp/echoes/commit/5a59bdd5) and [MusyX batch](https://github.com/PrimeDecomp/echoes/commit/94ac862d) each address related units together. Sunshine's [actor batch](https://github.com/doldecomp/sms/commit/e8a86b82) shows the tradeoff: dozens of matching functions can be useful progress while their TU is still not linkable. None of these examples implies that byte gain is proportional to lines changed.
3. **A short local loop is paired with a whole-build gate.** Prime's [contributor guide](https://github.com/PrimeDecomp/prime/blob/main/CONTRIBUTING.md) uses objdiff auto-rebuild and decomp.me scratches for help. Wind Waker's [guide](https://github.com/zeldaret/tww/blob/main/docs/decompiling.md#asking-for-help-with-a-function-by-sharing-a-decompme-scratch) shows how objdiff prepares a scratch context, then [checks the whole object](https://github.com/zeldaret/tww/blob/main/docs/decompiling.md#linking-a-100-matching-object), including data and relocations, against the final executable checksum. [Prime's CI](https://github.com/PrimeDecomp/prime/blob/main/.github/workflows/build.yml) builds all configured source across six versions and uploads maps and JSON reports; [Petari's CI](https://github.com/SMGCommunity/Petari/blob/master/.github/workflows/build.yml) also uploads these artifacts. I found documented scratch sharing, but no first-party evidence in the inspected projects that a permuter produced the measured gains. Dashboard updates are downstream of repeatable reporting, not a replacement for match verification.
4. **Coordination and retained compiler knowledge prevent duplicate investigation.** Wind Waker advertises [easy-object issues and a claim-by-comment workflow](https://github.com/zeldaret/tww/blob/main/docs/decompiling.md#choosing-an-object-to-decompile). Petari explicitly credits [new collaborators](https://github.com/SMGCommunity/Petari/blob/master/README.md#regarding-ai-usage). Sunshine records [MWCC code-shape observations](https://github.com/doldecomp/sms/blob/main/docs/AGENT_MATCHING_TIPS.md). Cross-platform [Persona 4's matching handoff](https://github.com/Raikaru/Persona4-Decompilation/blob/main/docs/first_party_matching_handoff.md) ranks live residuals, recompiles stored candidates, preserves failed probes and distinguishes exact function matches from source-linked code. This is a useful workflow model, though its PS2 toolchain and its fluctuating progress accounting do not transfer to DW4.

## What transfers to DW4

DW4 already has the essential [batch selection and strict verification workflow](../../AGENTS.md#recovery-throughput): choose related functions by verified-byte potential and dependency reuse; use targeted objdiff, exact code/data/full-relocation checks, source provenance, all-source build and pinned DOL checksum. The [October 1 ledger](../../PROGRESS.md#verified-numeric-snapshot) records **373,836 / 4,141,552 matched code bytes, 359,748 linked code bytes**; its 14,088-B match/link gap is small beside Petari's or Pikmin 2's, so a broad “link everything” campaign would have limited upside. The current fork's private-container CI constraint and local checksum-passing build are [documented](../../AGENTS.md#matching-build-verification). Its configured game category is empty, so category percentages are not gameplay coverage.

The limiting difference is source readiness. DW4 is **9.026% exact and only 9.054% fuzzy**, so almost every new cluster still requires reconstruction from stripped retail code. BFBB is 86.55% exact but 98.98% fuzzy, while the fast FFCC and Nintendo projects also have broad nonmatching scaffolds, maps, other-version code or debug information. Their agents can polish hundreds of already recognizable functions in parallel; DW4's current worker must often discover the types, ABI and source shape first.

The local workflow has also created useful machinery faster than it has productized it. `build/GDJEB2/analysis/` currently contains about 3,533 ignored files (305 MB), including 86 Python scripts and eight batch-specific ELF verifiers. That evidence is valuable, but later batches cannot depend on ignored one-off implementations. The next multiplier is to promote only the stable common core into small committed tools.

### Recommended adoption order

1. **P0 — build a private one-unit compiler/diff command.** Port the idea, not the BFBB implementation: read DW4's generated Ninja rule, compile one requested TU with the exact compiler/flags into a temporary directory, then emit strict compact objdiff results and match bands. It must not mutate `build/GDJEB2/report.json` or shared objects. This turns the current targeted-build convention into a safe primitive for concurrent workers and shortens the inner loop.
2. **P0 — consolidate verification, ranking and residual state.** Extract the common code/data/section/symbol/full-relocation comparison from the eight batch verifiers into one `tools/verify_unit.py`. Add a small `tools/rank_targets.py` that reports unmatched bytes, missing-vs-near-match bands, exact-vs-linked state, known compiler profile and dependency tags. Keep detailed candidate choices in `PROGRESS.md`; store machine state in generated analysis output, not another hand-maintained plan.
3. **P0 — start a compact DW4 matching playbook.** Distill only repeated, evidenced patterns: `-O4,s` signatures, retained-register causes, hidden-result ABI, pointer/value reloads, aggregate-loop signedness, virtual-slot calling shapes, relocation ownership and hard-stop conditions. Index each symptom to one experiment and one exact DW4 exemplar. This makes the 305 MB of local experiments compound without committing the debris.
4. **P1 — run a three-worker pilot, not an unbounded autonomous loop.** With four available slots, use one coordinator and three workers on disjoint source units in isolated Git worktrees or private shadow trees. Workers never edit shared headers or Git state without coordinator review; they return a patch/commit plus before/after unit evidence. The coordinator integrates sequentially, regenerates the authoritative report and runs the full source/ELF/map/checksum gates. Measure verified bytes per worker-hour and merge conflicts over two or three batches before scaling.
5. **P1 — preserve honest nonmatching scaffolds in one durable place.** The current experiment branches retain good partial reconstructions, but they are fragmented across 20 task branches. A persistent, clearly non-publishable `staging/scaffold-alchemy` branch could hold plausible NonMatching TUs and source context for parallel polishing; `work` should continue to receive only exact, source-linked subsets. Do this only after the private compile tool exists, and periodically delete or rewrite disproven scaffold rather than treating fuzzy progress as recovery.
6. **P2 — pursue a DW4 evidence multiplier.** Batch-export Ghidra/m2c views with project types and make them addressable by symbol. More importantly, adapt the existing [IGB metadata investigation](2026-09-29-starting-plan.md#4-recover-engine-types-from-alchemy-metadata) into a class/field/offset database. [AlchemyMetadataDumper](https://github.com/NefariousTechSupport/AlchemyMetadataDumper) demonstrates a runtime reflection dump architecture and includes GameCube platform guards, but its README lists only later Skylanders builds as supported; a DW4 port is a research hypothesis, not a drop-in tool. Search public/debug builds and other Alchemy games for symbol and layout evidence, recording provenance and validating every claim against GDJEB2.
7. **Keep the existing publication gates and metric distinctions.** Maintain exact versus linked bytes, exclude compiler artifacts, and use the pinned DOL checksum. A decomp.me scratch, permuter score, Ghidra reconstruction or fuzzy gain is a hypothesis until the local object and link gates pass.

### What not to copy

- Do not adopt FFCC's unconditional `codex exec --yolo` loop before targets, builds and Git state are isolated; its speed depends on infrastructure and continuous human integration that DW4 does not yet have.
- Do not chase the headline rates by bulk-importing SDK/library code or changing the reporting denominator. Separate game, engine and third-party-library gains.
- Do not parallelize shared-header edits. Those are multiplier changes, but BFBB's own `blast`/snapshot tooling exists because one header can silently perturb hundreds of units.
- Do not optimize for fuzzy score or function count. DW4's exact relocation and source-link standards are a strength worth preserving.

The realistic near-term target is not BFBB's 1 MB day: that burst relied on pre-existing source and debug DWARF that DW4 lacks. A private unit loop plus three disjoint workers should first aim to multiply the current exact-batch throughput without increasing rework. The larger step-change will come only if Alchemy metadata or a compatible donor build turns type and symbol discovery into reusable input.
