# Game RAM batch (beNDMWGameRam, 2026-11-07)

`0x8036D224..0x80378818`: the game RAM, the store of the persistent game state and the script API for it.
Every target is readable source; 12 functions and 4 `Ref<>` destructors link.

## What the code is

- **Data.** The manager holds the databases (`shinka` evolution, `pcTech` techniques, weapon, armor,
  ability chips, `enemy`, `eneatk` enemy attacks), a common data list and one data list per player. Each
  list holds named data objects (`HP`, `TSUYOSA`, `FLAGFOLDER`, ...), read with `fn_8031F3CC` and its
  siblings. `BASE_*` lists keep each Digimon's level, experience, skills and upgrade counts.
- **Players** (`beNDMWGameRamPlayer.cpp`). Selecting and loading a Digimon, the starting weapons
  (`INI_WEAPON1..3`), naming, equipping, the HP/MP setters with their HUD updates, the stat formulas with
  their level-band tables, and the full stat recompute (`fn_8036FDE8`).
- **Messages** (`beNDMWGameRamMessage.cpp`, `virtual90`). The 22 `beNDMWGameRam_Message` values:
  data access, game start/removal, HP/MP changes with effects, `CTRLPLAYER`, `CTRLITEM` (devices, disks,
  flags, BIT), `BKCHIPBITEXP` and `FIGHTCALC`. `FIGHTCALC` holds the 22 `FightCom` battle formulas: hit
  checks, criticals, player and enemy damage with variance, damage rank, status durations for both sides,
  debuffs, skill growth, experience award with level-up, and support magic (heal, cure, raise, speed,
  power and resist up). For readability `CTRLITEM`, `FIGHTCALC` and the support magic are separate static
  functions; the original has them inline in `virtual90`.
- **Data tables** in `.data` (`0x804EAD10..0x804EB18C`): level bands, HP/MP and stat band bases and
  slopes, per-stat database fields, technique ranks, elements, skill-growth chances, raise values.

## Constraints found

- **The string pool.** The original file uses string literals. MWCC pools them, with the file's float and
  int-to-float constants, at `0x80458F30..0x80459944` in first-use order and addresses them from one base
  register. An extern pool struct (reference, pointer or defined copy) never reproduces the base reuse;
  literals do (tested in `fn_8036DF70`). So every function that names a field can only match in one unit
  covering the whole file (`fn_8036CE1C..0x80378818`), `virtual90` included.
- **Out-of-line accessors.** `virtual90` calls one-line getters (`fn_803787xx`) that the other functions
  inline: the handler exceeded MWCC's inlining budget. The original source used accessor calls throughout.
- **Bounds-checked setters.** `fn_80378124`, `fn_8037833C` and `fn_803785D0` differ by one instruction:
  the original branches to the store past an explicit `blr`; ours folds it into `bgelr`. Four phrasings
  and `-O4,s` did not reproduce it.
- **`Ref<>` destructors.** Exception tables name the destructor of each held type. A type first emitted
  elsewhere gets a strong unit and its symbol renamed to the mangled name; types first emitted in this
  file stay in the unit that emits them (`virtual6C`'s).

## Tools

included, from the original exception index.
